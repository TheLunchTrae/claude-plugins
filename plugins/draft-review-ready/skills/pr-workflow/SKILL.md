# PR workflow

Follow every rule here for every PR you open or update. The user merges; you never merge, approve, or close a PR they didn't ask you to close.

## Before the PR

- **Issue first.** If the repo has Issues enabled (`gh repo view --json hasIssuesEnabled`, or `has_issues` from `gh api repos/{owner}/{repo}`), each PR has an issue. Reuse a matching open issue, otherwise create one. Apply only labels the repo already has (`gh label list`); never invent labels.
- **Commits.** A brief message saying what the commit changes, plus the reason when it isn't obvious. No work logs, no step-by-step history.
- **Dependencies.** For a vulnerable dependency, update it (direct dependency first). Use a package-manager override only when no released update fixes it.

## Opening

- Open every PR as a **draft**.
- The description says what the branch changes overall: purpose, then the changes as they stand now. Use the repo's PR template for its headings, but these rules win over it: no commit-by-commit history, no "Validation steps", testing or validation section.
- Link the issue with `Closes #N` when the PR resolves it.
- When the branch changes later, rewrite the description so it stays accurate.

## Review loop (required before "ready")

1. Start a **separate reviewer subagent** (a fresh agent, not a fork of you and not yourself). Give it the PR URL or diff and the repo's standards, not your own conclusions. Ask it to check state machines too: for every flag, status field, nullable field, cache, async or timer lifecycle, or UI flow the diff adds or changes, look for states that can get stuck, be lost or race, and for paths that enter or leave a state while skipping its usual handling. A full audit of the codebase is out of scope here; suggest the State Machine Audit plugin (`state-machine-audit`) for that.
2. Fix every significant finding. Skip a finding only with a stated reason.
3. Have the reviewer **re-check the fixes**. Repeat 2 and 3 until it reports nothing significant.
4. Only then mark the PR ready for review and report it.

Run the reviewer in the foreground, or in the background and end the turn only while it runs; it wakes you when it finishes. Don't end a turn with the loop open for any other reason unless you're blocked.

The plugin's Stop hook enforces this. It tracks PRs this session opens (as `draft`) and sees them marked ready, merged or closed. Report the steps in between by printing a marker line from the shell, with the PR's full URL:

```sh
echo "pr-workflow: reviewing <pr-url>"   # reviewer pass or fixes in progress
echo "pr-workflow: approved <pr-url>"    # reviewer approved; marking ready next
echo "pr-workflow: waiting <pr-url> <what you're waiting on>"
echo "pr-workflow: closed <pr-url>"      # closed, merged, or handed to someone else
```

- `waiting` is only for being blocked on the user or something external (their decision, a permission, a check you can't run). It ends at the user's next message; report it again if you're still blocked.
- Report a PR the hook missed as `draft` or `reviewing` to start tracking it.

## Stacked PRs

- Avoid stacking where you can. Keep squash merges.
- If PRs are stacked, before the user merges each one, rebase it onto the current default branch, retarget it there, and resolve conflicts. After the base PR is squash-merged, the next branch still carries the base's original commits, so it conflicts or shows them again until it's rebased.
- Check every PR against the current default branch (conflicts, CI) before calling it ready.

## Visual changes

- For UI or website changes, make mock-ups before building and screenshots of the result (Playwright where it fits), and share them in chat.
- Never commit screenshots or mock-ups, never put them in the PR body, and never push a branch or open a PR just to produce them.
- Deliver video as mp4 (H.264), never webm.

## Writing about PRs

- Mention every PR and issue as its full URL.
- Never include Claude session links, session IDs, or trigger or run IDs in commits, PRs, comments, code or docs. A `Co-Authored-By` trailer and a plain "Generated by Claude Code" footer are fine.
